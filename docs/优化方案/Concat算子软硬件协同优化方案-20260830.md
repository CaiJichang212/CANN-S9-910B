## 1. 结论

Concat 在本项目中不是数值计算算子，而是一个由 Scalar 编排、MTE2 读入、UB 暂存、MTE3 写出的多源数据搬运算子。其性能上限由以下三项共同决定：

1. GM 到 UB 的实际传输效率，以及 stride/非对齐搬运的指令效率；
2. 多输入、多分片带来的 DMA 描述符和 Scalar 发射成本；
3. 多核切分是否在并行度、每核工作量和 32 B 写所有权之间取得平衡。

当前实现在已测试范围内的正确性基础可靠，`TQueBind<VECIN,VECOUT>`、64 KiB 双缓冲、运行时 AIV 核数、二维 `DataCopyPad` 和非对齐整行回退均应保留；现有相对 32 B 列边界条件应保留并补充 GM 基址检查。本地证据不支持把 Vector 算力、UB bank conflict 或 L2 复用不足列为主因，当前应聚焦四类现象：

| 场景 | 证据支持的现象/诊断 | 当前代表证据 | 优先动作 |
|---|---|---|---|
| 大数据、较大连续片段 | MTE2 为主，部分 MTE3 | `score_shape_2024x3000_fp32`：MTE2 86.5% | 改善切核成本模型、搬运粒度和 tile 边界 |
| 64/255/256 路碎片 | 小 DMA 发射、32 B UB staging 跨度、输入定位 | `fragmented_256_fp16`：260.425 us，MTE2 87.0% | 输入边界感知列分区，减少额外交叉与描述符 |
| tiny / 单输入 / 低总量 | Scalar、TilingData、TPipe、过度启核 | `rank1_int32_exact`：Scalar 82.3%；46,200 B 用 40 核比 1-2 核慢 | 专用 TilingKey、Identity 快路、核数裁剪 |
| 低行数、超宽、非 32 B 行 | 整行回退导致并行度不足 | 16 MiB+2 B 单行 fp16：1 核、165.396 us、MTE2 93.3% | 仅对超大任务启用 32 B 写所有权的绝对 span 分片 |

推荐按以下顺序实施，每阶段独立构建、独立 A/B、可单独撤回：

0. `P0`：checked 64 位 shape/prefix，以及基址感知的 `rowPeriod` 行组安全加固；
1. `P1`：Identity 专用 TilingKey 和连续拷贝快路；
2. `P2`：为现有 Row/Column 选择器加入最小每核工作量和启核成本；
3. `P3`：为高输入数增加“输入边界感知”的非均匀列分区；
4. `P4`：仅为低行数、超宽、非对齐大任务增加安全 WideSpan；
5. `P5`：先 A/B 64/80/88 KiB tile；普通 `DataCopy` 仅作为无预设收益的独立微实验；
6. `P6`：最后再评估 tiny 静态 Tensor，通用路径继续保留 `TPipe/TQueBind`。

不建议恢复历史上的宽泛 Tiny、256 KiB 起步的通用 FlatSpan 或全局 checkpoint 方案；它们已有局部收益，但未通过全局门禁。

## 3. 官方资料整理

### 3.1 Concat 语义

华为 Concat 规格和 ONNX 官方定义一致：输入张量除拼接轴外形状相同，输入 dtype 相同，输出在指定轴上按输入顺序串接；负轴需要归一化到 `[0, rank)`。这意味着 Concat 不改变元素值，也不存在允许重排或丢弃数据的计算自由度。

| 资料 | 官方结论 | 对本项目的含义 |
|---|---|---|
| [华为 Concat 算子规格][H1] | 多个 Tensor 沿 axis 拼接，非拼接轴形状相同，输出 dtype 与输入相同 | Kernel 应按字节搬运，不应引入数值计算 |
| [ONNX Concat][H2] | variadic 输入沿指定轴连接 | 1-256 路只是实现上限，不改变顺序语义 |

### 3.2 910B / 220x 硬件特性

| 资料 | 官方结论 | 对当前 Concat 的约束 |
|---|---|---|
| [Ascend C 基本架构][H3] | AI Core 包含 Scalar、Vector/Cube、MTE1/MTE2/MTE3 等单元 | Concat 的有效执行单元是 Scalar、MTE2、MTE3 |
| [NPU 架构版本 220x][H4] | AIC 与 AIV 分离，每个核有独立 Scalar；AIV 使用 UB，UB 最小访问粒度为 32 B | 纯搬运使用 AIV；本方案保守采用物理 32 B block 唯一写所有权 |
| [PlatformAscendC][H5] | Host Tiling 可查询 AIC/AIV 核数、存储容量和带宽 | 禁止固定写死 20/40/48 核或 UB 容量 |

## 4. Concat 软硬件模型

### 4.1 统一数据视图

将输入 `i` 视为：

```text
X_i: [B, L_i, A]
Y:   [B, sum(L_i), A]

B = beforeDimSize
A = afterDimSize
d = dtypeSize
P_i = L_i * A * d             # 输入 i 的单行字节数
W = sum(P_i)                  # 输出单行字节数
S = B * W                     # 输出总字节数
```

输出位置 `(row, input, byteInPiece)` 映射为：

```text
src = X_i + row * P_i + byteInPiece
dst = Y   + row * W   + prefixBytes[i] + byteInPiece
```

因此，Concat 的逻辑最小数据量是读 `S` 字节、写 `S` 字节。本文统一使用：

```text
logical_bidirectional_bw = 2 * S / task_duration
```

该值是逻辑有效吞吐，不等于 profiler 中某一条物理总线带宽字段。

### 4.2 理论下界

在 MTE2 与 MTE3 能够流水重叠时，可用下式做成本分解。它不是精确周期公式：

```text
T_kernel >= T_launch + max(T_scalar, T_mte2, T_mte3)
T_mte2  >= logical_read_bytes / effective_read_bw + read_dma_count * issue_cost
T_mte3  >= logical_write_bytes / effective_write_bw + write_dma_count * issue_cost

rows_per_tile = min(floor(tile_bytes / AlignUp32(piece_bytes)), 4095)
```

对于彼此独立的输入 Tensor，每个与本核输出区间相交的非空输入至少需要一次独立 GM 读描述。除非上游改变存储布局或物理地址恰好连续，否则不能把不同输入的 MTE2 请求安全合并为一次连续读。这是 256 路小分片的结构性下界。

### 4.3 32 B UB staging 跨度

当前每个输入片段使用 `DataCopyPad` 搬入 UB。单个片段在 LocalTensor 中的行跨度按 32 B 向上对齐，这会限制单 tile 可容纳的行数。软件模型定义：

```text
model_ub_staging_ratio = sum(B * AlignUp32(P_i)) / S
```

2026-08-30 的模型给出以下 **UB staging 模型值**：

| case | 逻辑读 | 模型 UB staging | 比率 | 原因 |
|---|---:|---:|---:|---|
| `input_count_255_fp16` | 510 B | 8,160 B | 16.00x | 每路仅 2 B，却各占一个 32 B 搬入块 |
| `fragmented_256_fp16` | 16 MiB | 24 MiB | 1.50x | 30/34 B 片段分别对齐到 32/64 B |
| `fragmented_256_fp32` | 4 MiB | 5 MiB | 1.25x | 60/68 B 片段分别对齐到 64/96 B |
| `fragmented_256_int8` | 1 MiB | 2 MiB | 2.00x | 15/17 B 均对齐到 32 B |

华为 `DataCopyPad` 文档说明非对齐 CopyIn 会在 UB 端填充 dummy；它没有说明 HBM 必然按 32 B 多读。因此表中 8,160 B、24 MiB 等值不能称为物理 GM 流量。它们只说明 UB 行跨度、tile 行数和软件成本模型。仅优化二分查找仍不能根治 256 路路径，因为输入独立导致的 MTE2 API 调用数仍然存在。

### 4.4 场景分类

| 场景 | 数据形态 | 最合适的硬件映射 |
|---|---|---|
| `inputNum == 1` | 整个输出就是一个连续输入 | Identity 连续 span，多核按最小工作量裁剪 |
| `B` 大、`W` 非 32 B 对齐 | 多个独立完整行 | 基址对齐时按 `rowPeriod` 完整行组切核；否则单核或绝对 WideSpan |
| `W` 32 B 对齐、输入数少 | 行内有大连续片段 | Row × Column，二维 DMA |
| `W` 32 B 对齐、输入数多 | 大量短片段 | 输入边界感知列分区，减少被列边界额外切断的输入 |
| `B` 很小、`S` 很大、`W` 非对齐 | Row 路径并行度不足 | 仅超大任务使用绝对 32 B WideSpan |
| `S` 很小 | 启动和 Scalar 主导 | 少核、紧凑 Tiling；单 tile 时再评估单缓冲/静态 Tensor |

### 5.2 当前性能代价

| 问题 | 静态原因 | 动态证据 |
|---|---|---|
| 所有场景携带约 2 KiB Tiling | 两个 256 项 `uint32_t` 数组始终存在 | tiny 的 Scalar 占比高；历史紧凑 P0 对多数小 case 有收益 |
| 所有场景初始化 128 KiB 双缓冲 | `pipe.InitBuffer(..., 2, 64 KiB)` 无分流 | tiny/单 tile 仍支付 TPipe、队列和双槽初始化 |
| 代价模型没有启核惩罚 | `worstCost` 只计 DMA setup 与对齐后的 UB 成本代理 | 固定 46,200 B：1-2 核约 4.3 us，40 核 9.85 us |
| 均匀列宽会切断输入片段 | 列边界仅来自 512 B 和等宽候选 | fp16/fp32 256 路分别建模 532/286 次，理论输入交叉下界为 512/256 次 |
| 非对齐低行数无法列切 | 安全回退只按完整行并行 | 单行 16 MiB+2 B 仅 1 核，MTE2 93.3% |
| 全部走 `DataCopyPad` | 对齐主体没有普通 `DataCopy` 分支 | 只是可测假设；现有证据不能证明普通 `DataCopy` 更快 |
| 固定 64 KiB tile 有边界台阶 | 65,537 B 片段必须拆成两 tile | 65,536 B 为 5.740 us，65,537 B 为 6.331 us |
| shape 累加仍为 `uint32_t` | Host 182-208 直接乘加 | 当前测试未触发，但扩大 shape 会溢出；属于优化前置正确性风险 |
| 列边界只按相对 offset 对齐 | Host 97-133 假定输出 GM 基址至少 32 B 对齐 | 当前 PyTorch NPU 测试通过，但 `DataCopyPad` API 本身不承诺 GM 基址对齐；所有列路径必须运行时校验或按绝对地址切分 |
| `rowPeriod` 写入但 Kernel 未使用 | Host 90、246；Kernel 无对应读取 | 当前未复现错误；若要求物理 block 唯一所有权，应按行周期分核后 A/B |

当前 `blockCount <= 4095` 不是主动瓶颈。因为最小本地行占用为 32 B，64 KiB slot 最多容纳 2,048 行，所以当前实现先被 UB tile 限制，无法主动到达 4,095 行。

### 6.3 四条关键曲线

#### 输入数曲线

固定输出 2 MiB 时，1/2/4/8 路约 10.2-10.5 us，16 路 10.351 us，32/64 路升至约 13.2 us，128 路 20.172 us，256 路 39.020 us。输出字节不变而延迟随输入数上升，支持“输入交叉、API 调用和 Scalar 编排存在独立成本”的判断；由于 profiler 未导出 MTE 指令数，不能进一步声称硬件描述符数已被实测。

#### 启核曲线

固定总量 46,200 B 时：

```text
1核 4.434 us, 2核 4.332 us, 3核 4.517 us,
11核 5.600 us, 20核 6.941 us, 40核 9.850 us
```

当前“能用更多核就用更多核”的代价模型对小任务不成立。核数必须由最小每核字节和 DMA 数共同约束。

#### 64 KiB 边界

65,535 B、65,536 B、65,537 B 三点分别为 6.100、5.740、6.331 us；65,537 B 使模型 DMA 从 16 增至 24。扩大 tile 可能消除这个台阶，但必须保留双缓冲和 UB 预算。

#### 低行数超宽路径

`before=1` 的 16 MiB+2 B fp16 行因非 32 B 对齐只用 1 核，165.396 us；这不是非对齐 API 本身造成的，而是正确性保护与并行维度不足叠加。优化必须改变输出所有权划分，不能简单打开现有列切分。

## 7. 总体优化架构

建议通过 TilingKey 明确分离不同成本结构：

```text
if S == 0:
    ZERO_RETURN
elif inputNum == 1:
    IDENTITY
elif IsTinyAndUnderfilled():
    COMPACT_GENERAL
elif W % 32 != 0:
    if IsHugeLowRowWideSpanCandidate():
        WIDE_SPAN
    else:
        ROW_2D
elif inputNum >= highInputThreshold and HasEnoughAlignedInputBoundaries():
    BOUNDARY_COLUMN
else:
    GENERAL_COLUMN
```

所有阈值都由 shape、dtype、输入数、运行时 AIV 数、UB 容量和离线校准参数计算。禁止按官方 case 编号或猜测 shape 分流。

所有 `GENERAL_COLUMN/BOUNDARY_COLUMN` 路径在 Kernel 中还必须检查实际输出基址满足 32 B 对齐。若采用保守的物理 block 唯一所有权规则，Row 路径也不能任意按单行边界跨核，而要使用 `rowPeriod = 32 / gcd(W, 32)` 的行组。P0 是安全加固候选；当前实现未复现踩踏，仍需以性能和重复正确性 A/B 决定是否保留。

### 7.1 路径专用 TilingData

当前完整结构无论输入数都携带 512 个 `uint32_t`。建议按阶段增量引入结构，第一轮只增加 Identity key=2，默认 key=0 完整保留当前通用结构。CANN 8.5 宏式 TilingData 的注册关键代码如下：

```cpp
// 默认 key=0：继续注册当前完整结构，保护全部泛化 shape。
REGISTER_TILING_DATA_CLASS(Concat, ConcatCustomTilingData)

BEGIN_TILING_DATA_DEF(ConcatIdentityTilingData)
  TILING_DATA_FIELD_DEF(uint64_t, totalBytes);
  TILING_DATA_FIELD_DEF(uint32_t, usedCoreNum);
  TILING_DATA_FIELD_DEF(uint32_t, tileBytes);
END_TILING_DATA_DEF;
// 官方命名规则：${op_type}_${tiling_key}。
REGISTER_TILING_DATA_CLASS(Concat_2, ConcatIdentityTilingData)
```

Host 命中 Identity 时设置同一个 key 并序列化对应结构；其他场景显式设置默认 key=0：

```cpp
if (inputNum == 1) {
    context->SetTilingKey(2);
    ConcatIdentityTilingData t;
    // set fields, SaveToBuffer, SetDataSize
} else {
    context->SetTilingKey(0);
    ConcatCustomTilingData t;
    // preserve the current general tiling
}
```

Kernel 使用非负整数 key，并显式列出所有分支。为兼容当前构建链，`TILING_KEY_IS` 使用数值字面量：

```cpp
if (TILING_KEY_IS(2)) {
    GET_TILING_DATA_WITH_STRUCT(ConcatIdentityTilingData, t, tiling);
    RunIdentity(srcList, dst, t);
    return;
} else if (TILING_KEY_IS(0)) {
    GET_TILING_DATA(tilingData, tiling); // 默认注册的完整结构
    RunGeneral(srcList, dst, tilingData);
    return;
}
```

`Concat_2` 只是 TilingData 工厂的变体注册名，不改变公开算子名 `Concat`。后续 BoundaryColumn/WideSpan 只有在各自实验阶段才新增 `Concat_<key>`，不能第一轮一次注册六套结构。

关键约束：高输入数默认路径继续保留完整 offset。历史 P0 删除 offset 后，本地总和改善 6.24%，但三个 256 路 case 分别回退 0.89%、2.78%、5.39%；因此不能再次用全局压缩交换碎片路径性能。变体注册、Host `SetTilingKey`、序列化结构和 Kernel 读取结构必须四处一致，并以实际 `build.sh` 编译作为硬门禁。

## 8. 分阶段优化方案

### 8.1 P1：Identity 连续拷贝快路

#### 目标

`inputNum == 1` 时 Concat 与 dim 无关，等价于完整连续拷贝。当前通用路径仍解析 TensorList、扫描输入、构造完整 Tiling 并按列交集提交 DMA。

历史 P2.1 的独立证据中，`single_input_large_row_fallback` 从 8.753 us 降至 3.441 us，约 2.54x；该结果是历史本地 P0/P2.1 A/B，不是当前官方基线的新结果，但足以把 Identity 设为第一优先候选。

#### 关键代码

```cpp
uint64_t inputRowBytes = 0;
uint64_t totalBytes = 0;
if (!CheckedMul(catLen0, catUnitBytes, inputRowBytes) ||
    !CheckedMul(before, inputRowBytes, totalBytes)) {
    return ge::GRAPH_FAILED;
}
uint32_t used = SelectCoreNum(totalBytes, aivNum, minBytesPerCore);

// 每核只拥有完整的 32B body 单元；head/tail 由唯一核处理。
uint64_t dstAddr = reinterpret_cast<uint64_t>(yGm.GetPhyAddr(0));
Span span = SplitAlignedBodyByCore(dstAddr, totalBytes, used, coreId, 32);
CopyContiguous(input0, dst, span);  // 不做输入定位和行/列换算
```

`SplitAlignedBodyByCore` 和 `CopyContiguous` 是待实现的项目内 helper，不是 Ascend C 标准 API。前者必须把 `[dstAddr, dstAddr + totalBytes)` 分成唯一核处理的非对齐 head、按物理 32 B block 切分的 body 和唯一核处理的 tail；后者仍用 `DataCopyPad` 处理非对齐 head/tail。

#### Tiling 起点

- `minBytesPerCore` 扫描 32/64/128 KiB，不直接固定使用满核。
- 小于一个 tile 的请求先保持单核；是否使用单缓冲放到 P6 单独验证。
- body 按物理输出地址的 32 B block 划分，非对齐 head/tail 只允许一个核写。

#### 验收

- 单输入五个本地 case 固定 6 轮至少 5/6 更快；
- 单输入 P50 至少改善 `max(1 us, 5%)`；
- 92-case 总和不回退超过 1%；
- 四 dtype、非对齐尾部和特殊浮点位模式 bitwise Pass。

### 8.2 P2：带启核成本的统一 Tiling 模型

#### 目标

修复当前 `EstimateColumnCost` 只奖励减少单核字节、不惩罚过度启核的问题，同时让 Row 和 Column 使用同一套评价尺度。

#### 关键代码

```cpp
for (const Candidate &c : candidates) {
    if (c.usedCores > 1 && CeilDiv(totalBytes, c.usedCores) < minBytesPerCore) {
        continue;
    }
    Cost m = ModelExactWork(c); // 每核 logical bytes、API calls、input intersections、tail
    uint64_t score = byteWeight * m.worstLogicalBytes
                   + dmaIssueWeight * m.worstDmaCount
                   + inputLookupWeight * m.worstIntersections
                   + coreLaunchWeight * c.usedCores
                   + extraTileWeight * m.worstExtraTiles
                   + imbalanceWeight * m.tailSkew;
    KeepLowest(score, c);
}
```

`AlignUp32(pieceBytes)` 只用于计算 `rowsPerTile`、UB 容量和 `extraTiles`，不能作为物理 GM 字节数代入带宽项。该 score 是排序模型，不是硬件周期公式。

#### 校准方法

- `minBytesPerCore` 初始扫描 16/32/64/128 KiB；
- `dmaIssueWeight` 用固定字节、改变输入数的微基准校准；
- `coreLaunchWeight` 用 46,200 B 的 1/2/3/5/7/11/20/40 核曲线校准；
- 权重由同一平台上的正交微基准拟合，并对所有 shape 共用；`GetCoreMemBw` 只能给字节项提供粗粒度先验，不能推导 DMA 发射或启核成本。

#### 验收

- `micro_cores_01..40` 的选择不再落到明显劣化侧；
- tiny/scoring proxy 总和下降，`score_shape` 和 256 路大 case 不因裁核回退；
- profiler BlockDim 与 Host 模型逐 case 一致。

### 8.3 P3：输入边界感知的高输入数列分区

#### 目标

均匀 `colBlockBytes` 可能在输入片段中间切开，增加两个核分别处理同一输入的次数。对于高输入数，应优先在满足 32 B 输出安全的输入前缀边界处分列，然后在这些边界间做最小最大代价分区。由于官方 `DataCopyPad` 不要求 GM 基址对齐，相对 offset 为 32 B 倍数本身不足以证明物理 block 互斥；P3 必须先验证实际输出基址。

#### 关键代码

Host 侧只生成相对边界计划：

```cpp
for (uint32_t i = 0; i <= inputNum; ++i) {
    uint64_t boundary = static_cast<uint64_t>(prefix[i]) * catUnitBytes;
    if ((boundary & 31U) == 0) {
        eligible.push_back({i, boundary});
    }
}

// 在 eligible 上做连续分区，目标是最小化最慢列的
// logicalBytes + dmaWeight * dmaCount，而不是强制等宽。
ColumnPlan plan = MinimaxPartition(eligible, colCoreNum, rowSlices);
```

Kernel 侧在采用该计划前检查实际物理基址：

```cpp
uint64_t dstBase = reinterpret_cast<uint64_t>(yGm.GetPhyAddr(0));
if ((dstBase & 31U) != 0) {
    RunBaseAwareRowFallback(...); // P0：无对齐行组时只让 core0 工作
    return;
}
RunBoundaryColumn(plan, ...);
```

专用 Tiling 只为该路径保存每列的输入起止索引或字节起止，共不超过运行时 AIV 数，不给其他路径增加全局字段。

#### 可量化目标

| case | 当前模型 SubmitTile | 输入边界理论目标 | 说明 |
|---|---:|---:|---|
| `fragmented_256_fp16` | 532 | 512 或更接近 512 | 基址 32 B 对齐且保持两个 row slice 时，最低交叉数为 512 |
| `fragmented_256_fp32` | 286 | 256 | 基址 32 B 对齐且每个输入只属于一个列核 |
| `fragmented_256_int8` | 256 | 256 | 当前已在下界，不应改变 |

减少 20/30 次模型 DMA 不等于一定降低 20/30 次硬件指令，也不保证同比时延收益；必须结合 Scalar、MTE2 和 P50 验证。

#### 验收

- 四 dtype 256 路控制至少 3/4 改善；
- 任一项回退不超过 `max(2 us, 2%)`；
- `model_ub_staging_bytes`（CSV 历史列名 `aligned_read_bytes`）不增，`fragmentIntersections` 和 `SubmitTile` 模型不增；
- 92-case 总和至少 4/6 轮改善。

### 8.4 P4：超宽非对齐 WideSpan

#### 目标

解决 `W % 32 != 0` 且 `B` 很小导致 Row 路径只有 1-8 核的问题。历史 P2 将 FlatSpan 从 256 KiB 起广泛派发，完整矩阵未通过；新方案只处理“足够大到能摊薄边界和启核成本”的任务。

#### 初始门禁

```cpp
bool useWideSpan = (outputRowBytes % 32 != 0)
                && (beforeDimSize <= lowRowLimit)
                && (totalBytes >= hugeSpanThreshold)
                && (nonEmptyInputNum <= smallInputLimit)
                && (avgNonEmptyPieceBytes >= minPieceBytes);
```

建议从 `hugeSpanThreshold = 4/8/16 MiB`、`minBytesPerCore = 128/256/512 KiB` 做正交 A/B；不允许直接恢复历史的 256 KiB、40 核固定路由。

#### 关键代码

```cpp
// 以实际 dst 地址计算 32B head/body/tail，保证不同核不写同一物理 block。
uint64_t dstAddr = reinterpret_cast<uint64_t>(yGm.GetPhyAddr(0));
OwnedRanges ranges = BuildAbsoluteAlignedRanges(dstAddr, totalBytes, 32);
if (coreId == 0 && !ranges.head.empty()) {
    CopyLogicalRange(ranges.head); // 唯一核处理非对齐 head
}
Span span = SplitByMinWork(ranges.body, usedCoreNum, coreId);

Cursor cur = LocateOnce(span.begin);  // 初始化时定位 row/input/offset
while (cur.out < span.end) {
    uint64_t bytes = MinToInputRowOrSpanEnd(cur, span.end);
    CopyPiece(cur, bytes);
    AdvanceWithoutRepeatedBinarySearch(cur, bytes);
}
if (coreId == usedCoreNum - 1 && !ranges.tail.empty()) {
    CopyLogicalRange(ranges.tail); // 唯一核处理非对齐 tail
}
```

#### 安全条件

- head、body、tail 的输出 block 所有权唯一；
- 不使用跨核原子写或重叠 Pad；
- `BuildAbsoluteAlignedRanges` 必须基于 `GlobalTensor<uint8_t>::GetPhyAddr(0)` 的实际地址，而不是仅看相对 offset；
- 每核只在入口做一次除法/定位，热循环用递增游标；
- 任一输入、行或 span 的零长度均有终止保护。

#### 验收

- 六个宽行 case 至少 5/6 改善；
- 两个 `before=1` 锚点至少改善 10%；
- 非对齐尾部连续重复 10 次 bitwise Pass；
- scoring proxy 无 material 回退。

### 8.5 P5：tile 搜索与可选 DataCopy 对照

#### 普通 DataCopy 仅作对照

`DataCopyPad` 是当前已验证的通用正确性路径。华为官方文档没有承诺普通 `DataCopy` 在严格对齐时一定比 `DataCopyPad` 快，因此不得把它预设为生产快路。若仍需验证，只能作为独立构建的微实验，并严格转换参数单位：

```cpp
if (Is32BAligned(rowBytes)
    && Is32BAligned(srcGapBytes)
    && Is32BAligned(dstGapBytes)
    && rowBytes >= 32
    && rows >= 1 && rows <= 4095
    && rowBytes / 32 <= 65535
    && srcGapBytes / 32 <= 65535
    && dstGapBytes / 32 <= 65535) {
    DataCopyParams inParams{
        static_cast<uint16_t>(rows),
        static_cast<uint16_t>(rowBytes / 32),
        static_cast<uint16_t>(srcGapBytes / 32), 0};
    DataCopy(local, src, inParams);
    // queue dependency remains unchanged
    DataCopyParams outParams{
        static_cast<uint16_t>(rows),
        static_cast<uint16_t>(rowBytes / 32), 0,
        static_cast<uint16_t>(dstGapBytes / 32)};
    DataCopy(dst, local, outParams);
} else {
    DataCopyPad(...);  // 非对齐和大参数继续走当前路径
}
```

本次 CANN 8.5 头文件和官方 API 已核对：普通 `DataCopyParams` 的 `blockLen/srcGap/dstGap` 均以 32 B DataBlock 为单位；当前 `DataCopyPad` 使用的 `DataCopyExtParams` 中 `blockLen` 和 GM 侧 stride 以字节为单位。二者不能直接复用。若该对照未稳定超过测量噪声，应删除分支，继续统一使用 `DataCopyPad`。

#### tile 候选

```cpp
uint64_t ubBytes = QueryUbBytes(platform);
for (uint32_t tile : {64_KiB, 80_KiB, 88_KiB}) {
    if (2ULL * tile + otherUbBytes + safetyMargin <= ubBytes) {
        Evaluate(tile);
    }
}
```

首轮用三个独立构建分别修改 Host/Kernel 同一个 tile 常量，避免同时引入新的 Tiling 字段。当前配置 UB 为 192 KiB，88 KiB 双槽占 176 KiB，仍需把其他 UB 申请和安全余量计入预算。通用路径继续使用双缓冲；只有模型证明单核最多一次 SubmitTile 时，才在独立阶段测试单 buffer。

#### 验收

- 普通 `DataCopy` 对照只有在对齐组稳定改善且相邻非对齐组不回退时才保留，不预设 5% 收益；
- 65,537 B 边界的 SubmitTile 和 P50 下降；
- 若采集到流水图，MTE2/MTE3 overlap 不低于当前基线；若只有 summary ratio，则不得声称 overlap 已验证；
- UB 无越界，所有超大行和 stride 回退仍通过。

### 8.6 P6：tiny 静态 Tensor

#### tiny 静态 Tensor

官方说明静态 Tensor 可减少 TPipe 初始化的数百 ns 级开销，但需要手工 UB 和事件管理，且不能与 Pipe 框架混用。CANN 8.5 官方支持列表确认 Atlas A2 静态模式可使用 `DataCopyPad`。该路径必须由独立 TilingKey 编译，且静态分支内不能实例化 `TPipe/TQue/TQueBind`：

```cpp
if (TILING_KEY_IS(6)) { // 6: TINY_STATIC
    InitSocState();
    RunStaticSingleTileWithExplicitEvents(...);
    return;
} else if (TILING_KEY_IS(2)) { // 2: IDENTITY，仍是独立 Pipe 实现
    KernelIdentity op;
    op.Init(...);
    op.Process(...);
    return;
} else if (TILING_KEY_IS(0)) {
    KernelConcat op; // 只在 Pipe 分支中构造含 TPipe 的对象
    op.Init(...);
    op.Process(...);
    return;
}
```

实际接入时还要显式列出届时已存在的其他 key，不能使用无条件 `else` 兜底。手工事件 ID 不能使用 6/7，MTE2/MTE3 依赖必须成对，Kernel 入口必须调用 `InitSocState()`。该项最多优化 tiny 的固定成本，不会解决 Case5 级别的 MTE2 侧瓶颈，优先级低于 P1-P5。

## 9. P0：TilingData 数值安全与基址感知行组门禁

当前 `beforeDimSize`、`afterDimSize`、`totalCatLen` 和输入前缀都用 `uint32_t` 直接乘加。任何性能分流前先在 Host 使用 checked 64 位计算，并仅在确认可表达时写入对应 Kernel 字段：

```cpp
bool CheckedMul(uint64_t a, uint64_t b, uint64_t &out);
bool CheckedAdd(uint64_t a, uint64_t b, uint64_t &out);

uint64_t before = 0;
uint64_t after = 0;
uint64_t totalCat = 0;
if (!BuildShapeProductsChecked(context, before, after, totalCat)) {
    return ge::GRAPH_FAILED;
}
uint64_t catUnitBytes = 0;
uint64_t rowBytes = 0;
uint64_t totalBytes = 0;
if (!CheckedMul(after, dtypeSize, catUnitBytes) ||
    !CheckedMul(totalCat, catUnitBytes, rowBytes) ||
    !CheckedMul(before, rowBytes, totalBytes)) {
    return ge::GRAPH_FAILED;
}
```

`BuildShapeProductsChecked` 内部还必须用 `CheckedAdd` 构造每个输入的 prefix/`totalCat`，并拒绝负维度。若继续保留当前 `uint32_t` Tiling 字段，则在序列化前显式检查 `before/after/totalCat <= UINT32_MAX`；若升级为 64 位字段，Host/Kernel/注册布局必须同一次变更并做包内 `.o` 复核。

这是正确性门禁，不应与性能收益同时归因。

若采用保守的物理 32 B block 唯一所有权规则，Kernel 分流关键逻辑为：

```cpp
uint64_t dstBase = reinterpret_cast<uint64_t>(yGm.GetPhyAddr(0));
bool baseAligned32 = (dstBase & 31U) == 0;
if (useColumnPlan && baseAligned32) {
    RunColumnPlan(...);
    return;
}

// outputRowBytes 对齐时 rowPeriod=1；否则由 Host 写入
// 32 / gcd(outputRowBytes, 32)。基址对齐时，只有完整行组边界
// 保证相邻核的输出 span 边界落在物理 32B block 边界。
if (baseAligned32) {
    uint32_t totalGroups = CeilDiv(beforeDimSize, rowPeriod);
    uint32_t activeCores = Min(GetBlockNum(), totalGroups);
    if (GetBlockIdx() >= activeCores) return;
    RowRange rows = SplitWholeGroups(totalGroups, rowPeriod,
                                     beforeDimSize, activeCores, GetBlockIdx());
    RunRows(rows, ...);
    return;
}

// 官方未定义 DataCopyPad 跨核字节写原子性；无可证明的对齐边界时
// 先使用单核保守路径，超大任务由 P4 绝对 WideSpan 单独优化。
if (GetBlockIdx() == 0) RunRows({0, beforeDimSize}, ...);
return;
```

`CeilDiv`、`Min`、`SplitWholeGroups` 是项目内 helper，乘法需使用 64 位并 clamp 到 `beforeDimSize`。31/33/511/513 B 行的 `rowPeriod` 都是 32；当 `before=128` 时，保守模型最多只有 4 个完整行组可跨核。这可能显著改变现有 BlockDim，所以 P0 必须同时做性能 A/B，不能仅凭“更保守”直接提交。测试阶段还应临时记录 92-case 输出 `data_ptr() % 32`，确认当前 allocator 的实际行为，完成后删除日志。当前实现尚未复现踩踏，因此不能把它写成已确认 bug。

## 10. 实施顺序与 A/B 设计

### 10.1 单变量阶段

| 阶段 | 唯一主要变量 | 主要受益组 | 失败即撤回条件 |
|---|---|---|---|
| Baseline | 重建当前官方源码 | 全部 | 源码/运行库 hash 不一致 |
| P0 | checked shape/prefix + 基址/rowPeriod 行组门禁 | 全部 | 任一正确性或性能回退未解释 |
| P1 | Identity TilingKey | 单输入 | 单输入收益不稳定或全局回退 |
| P2 | 启核成本模型 | tiny、低总量 | 大 case 因裁核回退 |
| P3 | 输入边界列分区 | 64-256 路 | 256 路整体或全局回退 |
| P4 | 高门槛 WideSpan | 超宽低行数 | 写冲突、尾部错误、scoring proxy 回退 |
| P5a | tile 候选 | >64 KiB 片段 | 流水劣化或 UB 风险 |
| P5b | 普通 DataCopy 对照 | 严格对齐主体 | 无稳定收益或相邻 case 回退 |
| P6 | 静态 tiny | tiny 单 tile | 事件风险或收益低于复杂度 |

不要把 P1-P5 一次性合并后再测，否则官方五个 case 的差分无法定位收益来源。

### 10.2 本地门禁

每个阶段至少执行：

1. 当前 48 个固定/宽行 bitwise case；
2. seed `20260721`、`20260830`、`91000007` 各 100 个随机 case；
3. 四 dtype 混合连续 `(0,)` 契约；
4. 11 组高风险 case 各重复 10 次；
5. 92-case 6 轮、baseline/候选交替、每 case 30 task 丢首条；
6. 目标锚点的 PipeUtilization，必要时补 Memory/L2/ResourceConflictRatio；
7. Host 模型 BlockDim、SubmitTile、`model_ub_staging_bytes`（CSV：`aligned_read_bytes`）与 profiler BlockDim 一致性检查。

通用接受线：

- 正确性全部通过；
- 目标组至少 5/6 轮更快；
- 92-case 总和至少 4/6 轮更快；
- scoring proxy 总和不出现超过 1% 的未补偿回退；
- 任一 material 回退必须有明确、更大的关键路径补偿；
- 禁止使用单次最小值代替 P50 和成对轮次。

## 12. 明确不采用的方向

1. 不针对猜测的 Case4/Case5 shape 硬编码。
2. 不固定 `blockDim=20/40/48`，始终以 `GetCoreNumAiv()` 和工作量模型决定。
3. 不恢复 256 KiB 起步、默认 40 核的通用 FlatSpan。
4. 不恢复“所有小于 64 KiB 多输入都单核”的宽泛 Tiny。
5. 不给所有路径增加 checkpoint 数组；历史 P3 专项有效但全局 1/5 轮更快、总体回退 0.13%。
6. 不把 L2 驻留作为主要方向；Concat 是一次性流式读写，没有跨 tile 参数复用。
7. 不优化 UB bank；当前全部深采集冲突指标为 0，且无 Vector 计算。
8. 不引入 Cube、SIMT、CCU 或跨卡流水；目标 DAV_2201 的本算子只需 AIV 搬运。
9. 不插入全局 `PipeBarrier` 串行化 MTE2/MTE3。
10. 不删除 pybind 的 `.contiguous()`；Kernel 的连续地址模型依赖它。
11. 不声称可以普遍合并不同输入的 GM 读；不同 Tensor 的物理地址通常不连续。
12. 暂不实施“多路小片段搬入后在 UB 内按字节压紧”：当前没有覆盖四种注册 dtype 的已验证压紧原语，且它不减少 MTE2 输入请求数。

## 13. 预期收益与现实上限

| 优化 | 证据强度 | 预期影响 | 是否可能单独跨过 500 us |
|---|---|---|---|
| Identity | 历史局部 A/B 强 | 单输入可显著下降 | 未知，取决于隐藏 case 是否命中 |
| 核数成本模型 | 2026-08-30 微基准强 | tiny/中小任务稳健改善 | 不太可能单独完成 |
| 输入边界列分区 | 软件模型假设，尚未实现 | 目标是减少 256 路额外交叉和 API 调用 | 可能贡献 Case5，但无官方 shape 证据 |
| 高门槛 WideSpan | 诊断 case 支持，历史通用方案已有反例 | 超宽低行数可能恢复并行度 | 若隐藏大 case 命中，潜在收益大 |
| tile 搜索 | 64 KiB 边界微基准支持 | 可能减少跨 tile API 调用 | 更适合作为叠加收益 |
| 普通 DataCopy 对照 | 仅有 API 可用性，无性能证据 | 结果未知，不稳定即删除 | 不能作为主攻方向 |
| 静态 tiny | 官方原理支持，当前无 A/B | 数百 ns 级固定开销专项 | 不能作为主攻方向 |

要从 564.6515 us 降到 500 us，至少需要 64.6515 us 的官方净收益。仅做 tiny 固定开销优化不够；方案必须至少有一项命中 Case4/Case5 的大数据、多输入或低并行度根因。同时，top1 差距达到 357.977 us，说明最终竞争方案很可能需要多个专用路径协同，而不是对当前单一路径做一个参数微调。
