## 1. 核心结论

算子性能评测不是“运行一次 profiler 并找最大 ratio”，而是一套证据工程。可靠结论至少同时依赖以下六条链路：

1. **对象唯一**：源码、构建包、Kernel `.o`、Host/tiling 库、调用 wheel 和实际加载的动态库必须属于同一版本。
2. **环境可解释**：设备映射、外部占用、温度、容器、CANN、Python/Torch NPU、执行身份和环境变量必须可追溯。
3. **正确性先行**：性能采集前完成规格、随机、边界、特殊值和重复稳定性门禁；任何失败都终止性能流程。
4. **统计分层**：task、case、round、device、version 分层统计，不把不同层级样本无条件池化。
5. **模型与实测互证**：Host Tiling 和 Kernel tile/DMA 模型必须能解释 profiler 的 BlockDim、路径和转折点。
6. **结论边界明确**：本地诊断矩阵、历史 sanity check、候选 A/B 和官方成绩是四种不同证据，不能互相替代。

推荐把完整工作流固定为：

```text
冻结测试对象
  -> 隔离环境与设备门禁
  -> 私有构建和实际加载验证
  -> 完整正确性门禁
  -> 多卡校准
  -> 多轮延迟采集
  -> Host/Kernel 理论模型核对
  -> 锚点深度采集
  -> 四步流水与 Bound 分析
  -> 单变量候选 A/B
  -> 官方反馈闭环与证据归档
```

其中“冻结对象、正确性、多轮统计、模型核对、证据边界”比采集更多指标更重要。采集数据很多但对象不唯一、task 数不完整或统计层级混乱，结论仍然不可用。

### 2.2 实际得到的瓶颈图景

按本项目 AIV-only 诊断规则，本轮 10 个深采集锚点的主 Bound 分布为：

| Bound | 数量 | 代表场景 |
|---|---:|---|
| MTE2 Bound | 5 | 256 路 fp16/fp32 碎片、大连续 fp32、超宽非对齐、255 路小片段 |
| Scalar Bound | 1 | 极小 `rank1_int32_exact` |
| 无明显单一 Bound | 4 | 64 路 tiny、256 路 int8、单输入中等数据、宽行碎片控制 |

关键结论不是“Concat 都是 MTE2 Bound”，而是不同工作区间由不同成本主导：

- 大连续和 fp16/fp32 高碎片路径的 MTE2 ratio、时延和 DMA 模型一致支持“搬入/发射受限”是首要优化假设，但当前数据不能单独量化 HBM、L2、DMA setup 各自占比。
- 极小任务观测到 82.3% Scalar ratio 和明显的 Task-AIV 差值，与启动/循环/描述符等固定开销主导一致；未做隔离 A/B，不能进一步断言 TilingData、TPipe 或某段 Scalar 代码各占多少。
- 255 路极小分片同时有较高 Scalar 和 MTE2 ratio，与“描述符/循环/DMA 发射共同影响”一致，但仍是待验证的组合假设，不是已隔离根因。
- int8 碎片路径的 MTE3 ratio 较高但未达到本项目主 Bound 阈值，说明其观测结构与 fp16/fp32 不同；dtype、粒度和读写重叠的具体贡献尚未隔离。
- Vector ratio 近零，已采集的三类 Vector 冲突字段均为零，因此当前证据不支持 Vector 计算或这些 UB conflict 是主因；这不等于排除了所有 UB/同步问题。
- L2 命中率随数据规模、布局和一次性流式访问显著变化；低命中本身不等于应该强制缓存。

这一图景直接决定后续优化必须分路径验证，不能用一个宽泛路由覆盖 tiny、单输入、超宽非对齐和 256 路碎片场景。

## 3. 评测对象唯一性

### 3.1 为什么仅记录 Git commit 不够

自定义算子的真实执行链通常包含：

```text
Host 源码
  -> Tiling/Proto/OpAPI 动态库
  -> Kernel 编译产物 .o/.json
  -> 自定义 OPP 安装目录
  -> Python/C++ 调用扩展
  -> 动态链接器实际解析到的 API 符号
```

Git commit 只能证明源码版本，不能证明执行时使用了该源码构建出的包。共享 OPP、历史安装包、旧 wheel 和 `LD_LIBRARY_PATH` 顺序都可能造成 Host/Kernel/OpAPI 混配。

### 3.2 推荐的三层身份校验

| 层级 | 必须记录 | 本轮做法 |
|---|---|---|
| 源码 | Host、Tiling POD、Kernel、调用扩展 SHA-256 | 构建前与官方归档逐文件 `cmp` + SHA-256 |
| 构建物 | `.run`、wheel、Kernel `.o/.json`、`libcust_opapi.so`、tiling 库 SHA-256 | 安装后递归提取关键文件哈希 |
| 运行时 | 实际加载路径和目标 API 符号提供者 | `/proc/self/maps` + `dlsym`/`dladdr` |

只检查 `/proc/self/maps` 不够。本轮 GE 同时映射了多个 vendor 的同名 `libcust_opapi.so`，因此“私有库出现在 maps 中”不能证明 Concat API 来自它。最终通过按名称 `dlopen("libcust_opapi.so")`，再对 `aclnnConcatGetWorkspaceSize` 执行 `dlsym`/`dladdr`，确认实际符号提供者位于私有 OPP。

可复用门禁：

```text
源码哈希匹配
AND 包内关键文件齐全
AND 私有 op_api/lib 位于 LD_LIBRARY_PATH 首位
AND 目标 API 的 dladdr 指向私有 libcust_opapi.so
AND 最小真实调用 bitwise 通过
```

任何一项不成立，都不能开始性能采集。

### 3.3 官方指标语义与本项目数据口径

CANN 8.5 官方资料明确：

- `Task Duration(us)` 包含 task 调度到设备、设备执行以及响应结束，因此不是纯 Kernel/AIV 执行时间；
- `Block Dim` 是 task 运行 block 数，对应开发者配置的逻辑执行核数；
- Pipe ratio 是某类指令 cycle 数相对 total cycles 的比值；
- MTE2 表示 GM 到 AI Core 搬运，MTE3 表示 AI Core 到 GM 搬运；
- Memory、L2Cache 和 ResourceConflictRatio 分别描述带宽/搬运量、L2 命中与 miss allocate、以及已定义的 UB/执行资源冲突字段。

对应官方页面见 [OpBasicInfo](https://www.hiascend.com/document/detail/en/canncommercial/850/devaids/optool/atlasopdev_16_0098.html)、[PipeUtilization](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/850/devaids/optool/atlasopdev_16_0099.html)、[Memory](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/850/devaids/optool/atlasopdev_16_0095.html)、[L2Cache](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/850/devaids/optool/atlasopdev_16_0094.html) 和 [ResourceConflictRatio](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/850/devaids/optool/atlasopdev_16_0100.html)。

本项目使用原生 `msprof` task-based 导出的 `op_summary_*.csv`，官方链接主要用于核对字段语义；实际列是否存在、字段名和聚合层级始终以本轮 CSV 表头为准，不能假设与 `msprof op` 的独立 CSV 文件完全相同。

## 4. 环境隔离与设备门禁

### 4.1 隔离目标

性能环境的目标不是绝对“空闲”，而是状态可解释且采集期间不变化。至少需要冻结：

- CANN、驱动、固件、Python、Torch、Torch NPU 版本；
- 物理卡到容器逻辑卡的映射；
- 容器 image/container ID、PID 和 namespace；
- NPU 健康、温度、总线地址、HBM、进程占用；
- 自定义 OPP、wheel、运行库搜索顺序；
- 执行用户和文件所有权策略。

本轮从停止的 `cann850` 快照创建任务容器，只映射物理 5/6/7 到逻辑 0/1/2。物理 4 因运行容器显式映射而排除。每次 msprof 前都执行门禁，要求 5/6/7 的总线地址存在且 `npu-smi` 报告无进程；任务前后记录完整快照，最后停止容器。

### 4.2 物理卡和逻辑卡不能混用

容器内 Torch 使用逻辑 0/1/2，宿主 `npu-smi` 和报告使用物理 5/6/7。工程中应显式保存映射表，所有 CSV 同时保留 `physical_device` 和 `logical_device`。否则跨卡统计、问题复现和设备占用判断容易错位。

### 4.3 设备门禁应是硬失败

推荐每次采集前执行以下检查：

1. 目标物理卡健康状态为 OK；
2. 总线地址与预期拓扑一致；
3. 目标卡无任何 NPU 进程；
4. 容器只暴露计划内设备节点；
5. 上一次 msprof/应用进程已退出；
6. 快照写入独立证据文件。

发现非任务进程时应停止采集，而不是继续后在报告里解释噪声。未变化的设备状态是正式数据的前置条件。

## 5. 构建与运行环境踩坑复盘

本轮最耗时的问题不在 Kernel，而在 CANN、Conda、容器 UID、root-squash 和自解压包之间的组合。以下经验可直接迁移到其他算子。

| 现象 | 根因 | 最终处理 | 可复用原则 |
|---|---|---|---|
| `cmake` 报 `libldap.so.2` 缺少 `EVP_md2` | Conda Python 的 OpenSSL 经全局 `LD_LIBRARY_PATH` 污染系统 CMake | 为 CANN build 单独构造最小 LD 路径，不含 Conda `lib` | 构建环境和 Torch 运行环境必须分离 |
| makeself 尝试创建 `//selfgz...` | 数字 UID 无 passwd 项，进程 `HOME=/`，自解压默认临时根错误 | 设置任务专用 `TMPDIR` | 不依赖容器默认 HOME/TMP 推断 |
| TVM 创建 `/.tvm_test_data` 失败 | 本机 CANN 模块使用 `Path("~").expanduser()`，进程 HOME/账号解析落到 `/` | 设置专用 `TEST_DATA_ROOT_PATH` | CANN/TVM 缓存必须显式定向到任务临时目录 |
| `getpass.getuser()` 报 UID 不存在 | `docker exec --user <uid>` 不会自动创建 passwd 项 | 容器内注册固定 UID/GID | 使用数字 UID 前检查 passwd/group 语义 |
| 非 root 无法读 `opp/vendors/config.ini`、`scene.info` | 快照内 CANN OPP 为 `root:root 750` | 容器 root 只负责 CANN build/NPU/msprof，UID 9002 负责私有产物和离线汇总 | 不用宽泛 chmod 或加入 root 组绕过安装权限 |
| `opc` 报动态 Concat 输入数与内置 schema 不一致 | 第一阶段包没有安装进当前 CANN OPP，binary 阶段仍读取内置固定 schema | 保留项目两阶段 build，第一阶段临时安装到任务容器 CANN OPP | 动态输入算子不能把 package/binary 依赖随意合并 |
| 容器 root 在宿主 workspace 生成 `nobody` 文件 | `/home` 挂载存在 root-squash | 把 root CANN 构建移到容器任务 `/tmp` 的源码副本，最终包再由宿主 UID 复制 | root 任务不要直接写共享源码树和 tracked 证据 |
| 私有 OPP 无法重复删除 | `.run` 安装脚本会去掉 `vendors` owner 写位 | 重建前仅对本任务私有 OPP 执行 `chmod -R u+w` | 尊重安装脚本权限策略，恢复写位要精确到任务目录 |
| maps 中出现多个同名 `libcust_opapi.so` | GE 会加载多个 vendor OpAPI | 用 `dlsym`/`dladdr` 判断目标符号提供者 | 库“已加载”不等于 API“从该库解析” |
| 只读 `aicore.db` 打开失败 | 本轮默认 SQLite 连接在只读目录触发了写入相关错误 | 使用 `mode=ro&immutable=1` URI | 仅在确认采集已结束、数据库不会再变化时使用 immutable；原始数据解析保持只读 |

这些处理可由官方资料交叉核验：Python 3.9 的 [`expanduser`](https://docs.python.org/3.9/library/os.path.html#os.path.expanduser) 在 Unix 上优先使用 `HOME`，否则查询 passwd；[`getpass.getuser`](https://docs.python.org/3.9/library/getpass.html#getpass.getuser) 在环境变量均为空时回退到密码数据库；Docker 的 [`--user`](https://docs.docker.com/reference/cli/docker/container/run/#user) 接受 UID/GID，但不承诺为数字 UID 自动创建 passwd 项；Python [`sqlite3` URI](https://docs.python.org/3.9/library/sqlite3.html) 和 [SQLite URI](https://www.sqlite.org/uri.html) 分别定义 `mode=ro` 与 `immutable=1`。`immutable=1` 会跳过锁和变化检测，只有文件生命周期真正冻结时才安全。

说明：上述失败现象来自本轮终端现场记录，最终脚本保留了修复方案，但早期失败日志被后续成功构建日志覆盖。它们属于工程复盘证据，不属于性能数值证据；后续流程应把每次失败尝试保存为独立、不可覆盖的日志。

### 5.1 推荐的身份分工

当现有镜像的 CANN 只能由 root 读取时，推荐以下最小权限分工：

| 工作 | 身份 | 写入位置 |
|---|---|---|
| CANN 两阶段构建 | 容器 root | 容器任务 `/tmp` |
| NPU 真实调用、msprof | 容器 root | raw 临时目录，完成后向汇总 UID 开放只读访问 |
| 私有 OPP/wheel 安装 | 宿主 UID 对应容器用户 | workspace 的 ignored `private/` |
| CSV 解析、报告、哈希 | 宿主 UID 对应容器用户 | tracked 证据目录 |
| root 采集文本归属修复 | 宿主 UID 原子复制替换 | tracked `metadata/` |

更理想的长期方案是预制包含固定用户、可读 CANN OPP 和 Python 3.9/Torch NPU 的评测镜像，从源头消除 root 分工。但在不能修改公共镜像时，上述分工比扩大 CANN 目录权限更可控。

## 6. 正确性门禁设计

### 6.1 正确性不是性能流程的附属步骤

纯搬运算子也可能因地址、stride、padding、输入连续性、跨核写冲突和尾块处理产生隐蔽错误。性能变快但输出偶发错误的候选必须立即淘汰。

本轮采用四层正确性矩阵：

| 层级 | 目的 | 典型内容 |
|---|---|---|
| 固定规格 | 覆盖已知 dtype/rank/axis/shape/input count | 42 个固定 case |
| 鲁棒性压力 | 覆盖超宽、255/256 路、零长度、大分片 | 6 个宽行及多组边界 |
| 随机正交 | 防止实现只适配人工 case | 3 个种子各 100 个 rank 1 到 7 case |
| 契约与稳定性 | 覆盖 API 特例和偶发错误 | 四 dtype 混合 `(0,)`；11 组 repeat10 |

### 6.2 纯 Copy 算子优先使用 bitwise oracle

Concat 不做数值计算，fp16/fp32 应按位比较，而不是只用 rtol/atol。按位 oracle 能覆盖：

- `+0/-0`；
- `Inf/-Inf`；
- NaN payload/位模式；
- 未初始化或错位读取；
- dtype 无意转换。

整数使用精确相等。任一 case/iteration 失败应立即退出，不继续采集性能。

### 6.3 调用层契约也要纳入门禁

本轮 Kernel 按连续地址读取，`torch.split` 产生的 view 必须在调用侧转为 contiguous。该条件不是测试辅助，而是运行契约的一部分。评测应记录并验证：

- 输入是否 contiguous；
- output shape 由谁推导；
- 空输入和不同 rank 空张量的框架语义；
- 动态 TensorList 最大输入数；
- 正负 axis 归一化。

## 7. 性能矩阵的正交化设计

### 7.1 不要把“case 多”误认为“覆盖好”

高质量性能矩阵要能回答“改变哪个因子导致性能变化”。至少分成三类：

1. **评分/业务代理**：尽量贴近公开规格或真实业务分布；
2. **鲁棒性压力**：验证输入上限、超宽、极端碎片和回退路径；
3. **正交微基准**：固定其他变量，只改变一个结构因子。

汇总报告必须分开这三类。压力矩阵总和不能被称为业务性能，更不能替代官方分数。

### 7.2 本轮 32 个微基准的设计逻辑

| 维度 | case 设计 | 要回答的问题 |
|---|---|---|
| 输入数 | 固定 2 MiB fp16 输出，1/2/4/.../256 路 | TensorList、输入循环和小 DMA 发射何时成为主成本 |
| 核数扩展 | 固定 46,200 B int8，总量不变，row 路径使用 1/2/3/5/7/11/20/40 核 | tiny 固定工作量是否值得增加核数 |
| 对齐 | 31/32/33 B 与 511/512/513 B | 32 B 写安全条件、512 B 列策略和 padding 成本 |
| tile 边界 | 65535/65536/65537 B 片段 | `pieceBytes > 64 KiB` 线性回退的真实转折 |
| 行数边界 | 2047/2048/2049 与 4094/4095/4096 | 64 KiB tile 下二维 DMA 的实际行数上限 |

关键经验是：**用例名字不能证明命中分支，必须由模型证明。**

例如当前 Kernel 的最大二维行数为：

```text
maxRows = min(65536 / AlignUp32(pieceBytes), 4095)
```

因为最小对齐 piece 为 32 B，所以 `65536 / 32 = 2048`，4095 永远不会成为主动上限。为了让每个列核真正看到 2047/2048/2049 行，本轮构造 40 路 × 32 B 分片，使 Host 选择 40 列核、1 个 row slice。实测模型 `SubmitTile` 在 2048 到 2049 时由 40 增至 80。

这比简单构造 `beforeDim=4095` 更严格。后者经过多核切分后，每核行数可能远小于边界，实际根本没有覆盖 `blockCount` 路径。

### 7.3 微基准也能证伪直觉

固定 46,200 B 的核扩展曲线显示，1 到 2 核略有收益，此后核数越多整体越慢，40 核 P50 明显高于 1 核。这说明：

- “可用 40 核”不等于“应该用 40 核”；
- tiny 场景的核启动、描述符和 DMA 发射成本可能超过并行收益；
- BlockDim 应由工作量和粒度模型决定，而不是越大越好。

## 8. 多卡校准与噪声控制

### 8.1 校准应覆盖两种时间尺度

只校准大 case 会掩盖启动噪声，只校准 tiny 会放大绝对误差。本轮每张卡同时校准：

- tiny：`rank1_int32_exact`，组内 CV 阈值 15%，卡间 P50 极差阈值 10%；
- large：`score_shape_2024x3000_fp32`，组内 CV 阈值 5%，卡间 P50 极差阈值 5%。

异常卡先检查占用，再只重测一次；仍异常则从聚合中排除并记录。最终三卡均纳入，tiny/large 卡间极差分别为 8.86% 和 3.96%。

### 8.2 阈值不是通用常数

上述 15%/10% 和 5%/5% 是本项目在微秒级 tiny 和几十微秒大任务上的工程阈值。迁移到其他算子时，应先用 pilot 数据估计噪声底：

```text
within_case_cv = population_std(hot_tasks) / mean(hot_tasks)
cross_card_spread = (max(card_p50) - min(card_p50)) / median(card_p50)
```

阈值应满足：能识别明显异常，又不会因 tiny 的量化/调度噪声频繁误报。

### 8.3 当前设计的局限

正式延迟每张卡只有两轮，六轮总序列能观察卡间一致性，但卡效应与轮次效应仍部分混杂。若目标是严格比较卡间差异，建议：

- 每卡至少 3 轮；
- 使用 Latin square 或平衡轮次顺序；
- 同一个关键 case 在每张卡都重复采集；
- 将温度和时钟状态加入每轮 manifest。

## 9. 延迟采集与统计分层

### 9.1 批量采集优于每 case 一个 msprof

msprof 启动和导出成本远高于许多微秒级算子。本轮每轮只启动一个 msprof，程序按确定性顺序运行 92 个 case，每个 case 固定发出 30 条 Concat：

```text
每轮 Concat task = 92 × 30 = 2760
六轮原始 Concat = 16560
六轮热样本 = 92 × 29 × 6 = 16008
```

解析器按已归档 order file 的固定 30-task 边界切组，并断言原始 task 总数。这样既降低导出开销，又保留 case 级统计。

深采集同理：每卡每个 metric 用一个 10-anchor batch，而不是 10 个独立 msprof。三卡七组 + sample 从潜在 240 个进程降为 24 个进程。

这里的“每个 metric 一个进程”是本项目基于原生 `msprof`、历史 task 分组和解析链路作出的采集设计，不是所有 CANN 工具的强制限制。CANN 8.5 官方 [`msprof op`](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/850/devaids/optool/atlasopdev_16_0082.html) 支持 `--aic-metrics=Default` 或逗号分隔的多个指标。切换工具或合并指标可能改变 replay、输出格式和任务对应关系，必须先做小规模对照，不能直接替换现有证据口径。

### 9.2 每层统计的正确口径

| 层级 | 样本 | 推荐统计 |
|---|---|---|
| task | 同 case 同 round 的 30 条 | 丢弃首条，保留 29 条热样本 |
| case-round | 29 条热 task | P50、P95、mean、CV、min/max、AIV P50、BlockDim |
| case | 多个 round 的 case-round | round P50 的中位数、跨轮 CV、范围 |
| round | 同一轮所有 case | case P50 之和，仅作固定诊断矩阵汇总 |
| device | 属于同一物理卡的 rounds | 单独保留，不先与其他卡池化 |

`Task Duration` 是包含调度、设备执行和响应结束的 task 级时延。纯设备侧执行另看 `aiv_time(us)`；二者差值可以提示存在 task 级固定成本，但不能在没有隔离实验时直接拆成框架、Tiling、TPipe 或 Kernel 各自开销。本文用 `2 × output_bytes / Task Duration` 计算的是 task 级逻辑双向有效吞吐，不是硬件活跃带宽或 HBM 峰值利用率。

禁止做法：

- 直接把 6 轮的 174 条热 task 混在一起求一个 P50，丢失 round/card 层级；
- 取单次最小值作为性能；
- 不丢弃首条冷启动；
- task 数不足仍继续汇总；
- case 顺序变化但未归档 order file；
- 将本地 92-case P50 和称为官方分数。

### 9.3 诊断总和的含义

本轮 92-case 跨轮 case P50 之和为 1784.734 us。该数字只回答：在固定矩阵、固定权重下，整体是否发生大范围变化。它不代表：

- 官方隐藏 5 case 总分；
- 真实网络 case 分布；
- 每个 case 同等业务频率；
- 候选相对基线的加速比。

## 10. Host/Kernel 理论模型

### 10.1 模型至少要覆盖什么

对数据搬运类算子，模型应从 case 参数推导：

- `beforeDim`、`afterDim`、concat axis、dtype bytes；
- 输出行字节数、输入前缀 offset；
- Host 选择的 splitMode、row slices、column cores、BlockDim；
- 每核行/列范围；
- 每核与输入片段的交集数；
- stride/linear 回退条件；
- `SubmitTile` 次数、逻辑字节、对齐字节、平均 B/DMA；
- tile、blockCount 和 uint32 参数边界。

本轮 Python 模型逐行复现 `ChooseSplit`、二分输入定位、`SubmitStridedPiece` 和 `SubmitLinearRange`。六轮 92-case 共 552 个 case-round 的 profiler BlockDim 全部与预测一致。

### 10.2 模型是分析门禁，不只是报告附表

BlockDim 不匹配可能意味着：

- 实际加载了另一版本 Host/Tiling；
- case 参数或 dtype 解释错误；
- 模型遗漏了 tie-break/对齐条件；
- profiler 分组错位；
- order file 与运行顺序不一致。

因此解析器应在计算性能结论前先断言模型一致。模型不一致时应停止分析，而不是继续用错误路径解释 ratio。

### 10.3 模型值和硬件计数必须分栏

本轮 Memory CSV 没有导出 MTE 指令数字段，因此报告使用模型 `SubmitTile` 次数表示预计 MTE2/MTE3 发射数，并明确标记为模型值。不能把它写成“profiler 实测 DMA 指令数”。

通用规则：

- profiler 有字段时，保留实测与模型两列并比较；
- profiler 无字段时，模型值用于解释相对趋势，不用于宣称硬件精确计数；
- 模型要先通过 BlockDim/路径/边界转折验证。

## 11. 四步流水与 Bound 分析

### 11.1 Step 1：Tiling 理论建模

所有算子都必须执行。输出不仅是 tile 大小，还包括多核切分、Buffer 规划、分支覆盖和理论成本。本轮 Concat 属于 Conversion/纯搬运类，通用技能没有现成 Concat 模型，因此以真实 Host/Kernel 源码为准复现。

### 11.2 Step 2：卡间流水

仅通信或 MC² 算子执行。Concat 无 HCCS/SHMEM/集合通信，三卡只是独立复测设备，不构成卡间流水，因此明确跳过。

迁移到 MC² 时不能沿用本轮简化：必须增加多 rank 采集、跨 rank 最大值、通信/计算隔离测试和 MTE2 通信等待污染判定。

### 11.3 Step 3：核间流水

仅有跨核同步或核间依赖的算子执行。Concat 各核写互斥输出，无 barrier/atomic/跨核数据依赖，因此跳过同步流水分析，但仍检查 BlockDim 和理论工作分配。

### 11.4 Step 4：单核流水与主 Bound

CANN 8.5 官方文档定义各 Pipe ratio 的含义，但不规定“超过多少就是主 Bound”。本项目为了跨 case 一致归类，采用内部诊断阈值；它不能直接迁移为其他算子或 SoC 的验收标准。

本轮 Concat 为 AIV-only，实际解析器只读取 `aiv_mte2_ratio`、`aiv_mte3_ratio`、`aiv_vec_ratio`、`aiv_scalar_ratio`，按以下顺序分类：

1. MTE2 > 80%，或 MTE2 是这四项中的最大值且 > 70%；
2. VEC > 80%；
3. MTE3 > 80%；
4. Scalar > 80%；
5. 否则为无明显单一 Bound。

实际实现见 [summarize_deep.py](../../Concat/perf_eval/20260830_bottleneck/scripts/summarize_deep.py)。Cube/FIXP 不在本轮 AIV-only parser 中；对 Cube/Mix 算子应增加相应字段，并重新定义经验证的分类规则。

官方把每个 ratio 分别定义为该类指令 cycle 数相对 total cycles 的比值，并未把它们定义成一组互斥分类。因此不能强制 MTE2、MTE3、Scalar 等相加为 100%；某个具体 case 是否以及如何重叠，需要 instruction timeline 或隔离实验确认，不能只由聚合 ratio 反推。

### 11.5 深采集锚点如何选

锚点不应只选最慢 case。推荐从以下维度各选代表：

- tiny/启动开销；
- 中高输入数；
- 255/256 路上限；
- 不同 dtype 的碎片化；
- 大连续；
- 单输入；
- 超宽非对齐；
- 宽行碎片；
- 延迟高波动；
- 低有效带宽。

本轮选择 10 个锚点，三卡分别采 Pipe、Arithmetic、Memory、MemoryL0、MemoryUB、L2、ResourceConflict 和 Sample。

### 11.6 跨指标解释规则

| 现象 | 正确解释 | 不应直接得出的结论 |
|---|---|---|
| MTE2 高 + 模型平均 B/DMA 小 | 小搬运/发射可能是瓶颈 | HBM 一定已打满，或模型值等于硬件计数 |
| MTE2 高 + 有效带宽高 | 大连续搬运接近主导 | 增加更多核一定更快 |
| Scalar 高 + tiny | 与固定启动/循环/描述符成本较高一致，具体来源待隔离 | Scalar 代码必然有 bug，或已证明是 TPipe/TilingData |
| L2 hit 低 + 一次流式访问 | 复用弱可能是语义决定 | 必须打开/增强缓存 |
| 已采 conflict 字段全零 | 当前数据不支持这些冲突是主因 | 排除了所有 UB/同步问题 |
| MTE2/MTE3 同时高 | 两项不是互斥分类，可能存在流水并行或共享带宽 | 两者占比可直接相加，或已证明具体重叠比例 |
| `task_cyc=0` | 本轮该字段无有效数据，原因未定位 | 平台永久不支持，或所有核耗时为 0/完全均衡 |

本轮三张卡的 `task_cyc` 均为 0，因此不反推频率、不生成逐核时长、不做负载均衡结论。即使后续探针出现非零值，也必须继续验证 replay/task/core 映射、cycle 口径和频率换算；“非零”只是必要条件，不是逐核分析充分条件。

CANN 8.5 将 L2 读通道字段定义为 `ai*_r*_read_cache_hit/miss_allocate`，其中 `r*` 是通道通配。通用解析器必须动态枚举实际 CSV 中出现的所有读通道，不能硬编码 r0/r1。本轮解析脚本已按前缀/后缀动态聚合，并以实际表头为准。

## 12. 候选优化的严格 A/B

本轮属于基线刻画，不是候选 A/B。进入优化阶段后，应复用同一环境、矩阵、模型和解析器，并增加以下约束。

### 12.1 单变量原则

每个候选只改变一个可命名假设，例如：

- 单输入 Identity；
- tiny Tiling/TPipe 开销；
- 256 路 checkpoint；
- 对齐 DataCopy 快路；
- 超宽非对齐安全并行。

不要同时修改 TilingData、入口对象、核数、DMA API 和路由阈值后再根据总和归因。

### 12.2 AB/BA 交替

推荐每轮同卡运行两个版本并交替顺序：

```text
round 1: baseline -> candidate
round 2: candidate -> baseline
round 3: baseline -> candidate
...
```

每版本使用相同 case 顺序、相同 task 数和独立私有 OPP。禁止共享目录覆盖后仅靠环境变量猜测当前版本。

### 12.3 五类接受门槛

| 门槛 | 例子 | 目的 |
|---|---|---|
| 正确性 | 完整矩阵 + 路由专项 repeat10 全过 | 防止性能换错误 |
| 总体 | 至少 4/5 或 5/6 轮总和改善 | 排除偶然单轮收益 |
| 局部 | 关键 case 改善超过 `max(abs_threshold, relative_threshold)` | 证明目标路径真实收益 |
| 回归 | 非目标 case 无 material 回退，或有明确可量化补偿 | 防止局部优化破坏全局 |
| 结构 | BlockDim/路径/指标变化与设计预期一致 | 避免把噪声当因果 |

历史 P0/P2/P2.1/P3 提供了重要反例：

- P0 总体有收益，但 256 路碎片 case 存在回退；
- P2 Identity 局部收益明显，但宽泛 Tiny/FlatSpan 路由导致总体门禁失败；
- P3 checkpoint 改善特定 256 路路径，却未通过全局多轮验收；
- 当前源码最终恢复为官方基线，说明历史候选只能作为假设库，不能作为当前结论。

通用经验：**专项 case 变快只是必要条件，不是默认启用条件。**

## 14. 常见反模式

| 反模式 | 风险 | 替代做法 |
|---|---|---|
| 只跑一次取最小值 | 极易受 DVFS/调度噪声影响 | 30 task、丢首条、P50/P95/CV、多轮 |
| 单卡无校准 | 无法区分卡差和实现差 | tiny+large 三卡校准，异常重测一次 |
| 并发 msprof | 设备、导出和系统负载互相污染 | 全流程串行采集 |
| 每 case 一个 profiler | 导出开销巨大，状态漂移更多 | batch 多 case，固定 task 边界 |
| 不断言 task 数 | 少采/多采仍被静默统计 | parser 硬断言 expected count |
| 把本地总和当官方分数 | 证据越界 | 单独标注 diagnostic sum |
| 从官方时延反推隐藏 shape | 容易硬编码并失去泛化 | 只用反馈判断候选方向，不猜 shape |
| case 名字代替分支证明 | 实际可能被多核切分绕开边界 | Host/Kernel 模型 + profiler BlockDim |
| 只看一个 ratio | 容易误判重叠、固定开销和共享带宽 | Pipe + Memory + L2 + conflict + 模型交叉分析 |
| 低 L2 hit 就强制缓存 | 流式算子可能无复用 | 先判断数据复用与污染收益 |
| `task_cyc=0` 仍算逐核耗时，或把零值归因成平台永久不支持 | 产生伪结论 | 标记本轮 unavailable，停止逐核推断并保留原因未定位 |
| maps 中看到私有库就认为生效 | 同名 vendor 库可能同时加载 | 对目标 API 做 `dlsym`/`dladdr` |
| 直接在共享 OPP 覆盖版本 | Host/Kernel/wheel 易混配 | 每版本独立私有 OPP |
| 整体恢复历史优化包 | 无法确认单项因果 | 历史补丁只作假设库，逐项移植 A/B |
| 采集和汇总都用 root 写 workspace | root-squash/所有权污染 | root 写任务 `/tmp`/raw，宿主 UID 写 tracked 证据 |

## 15. 下一轮流程改进

本轮流程已经可复跑，但仍有以下可改进点。

### 15.1 预制评测镜像

将固定 UID、Python 3.9、Torch NPU、CANN 8.5 和可读 OPP 权限预制进专用镜像，减少 root 分工、Conda/CMake 动态库冲突和临时用户注册。

### 15.2 增加不可变 run manifest

每次采集生成一个 manifest，包含：

- source/artifact/runtime hash；
- container image ID；
- case manifest/order hash；
- physical/logical device；
- metric、round、task count；
- profiler/CANN version；
- 开始/结束时间。

parser 读取 manifest，并拒绝用新包汇总旧 raw。当前一键 host 流程在发现已有 raw 时会拒绝重建复用；单独执行的 profile stage 仍有“文件存在即 skip”能力，因此后续若要支持安全断点续采，还必须增加 runtime hash 一致性检查，而不是绕过 host guard。

### 15.3 先做能力探针

在 24 个深采集 batch 前，先用一个小锚点探测：

- sample `task_cyc` 是否非零；
- Memory CSV 是否包含 MTE instruction/data fields；
- 各 metric 实际列名；
- SQLite 是否可读。

若能力探针仍得到零值，应先记录“本轮不可用”并检查工具、配置、版本和设备支持信息。是否继续三卡 sample 取决于验收是否要求跨卡复核；不能仅凭零值宣布平台永久不支持。若得到非零值，仍需验证 task/core 映射和换算口径后再决定是否用于逐核结论。

### 15.4 更平衡的跨卡设计

严格性能回归可采用每卡多轮 Latin square，将 card、round、order、version 效应分离。当前六轮两次/卡适合基线刻画，但对 1% 以内候选差异仍不够强。

### 15.5 自动锚点选择

从 latency CSV 自动选择：最慢、最高 CV、最低有效带宽、每个 dtype/input bucket/size bucket/split path 的代表，再人工补充语义锚点，降低主观选择偏差。

### 15.6 原始数据容量控制

本轮 raw 约 575 MiB。建议在完整性校验后：

- 记录原始文件清单和 SHA-256；
- 对 PROF 目录归档压缩；
- 保留 CSV/SQLite 最小必要原件；
- 明确 raw 的保留周期和重建成本。

### 15.7 增加仿真/时间线证据

本轮主要依据 task-based ratios，未得到可用逐核 cycle，也没有单独的 simulator 时间线。若候选涉及 DoubleBuffer、MTE2/MTE3 overlap、flag/barrier 或核间负载，应补充仿真流水图或可解析 timeline，不能仅靠聚合 ratio 推断重叠细节。

## 16. 标准作业流程

### Phase 0：定义目标与证据边界

- 明确是基线刻画、候选 A/B、标杆对比还是官方提交验收；
- 明确评分代理与鲁棒性压力矩阵；
- 明确本地数据不能代表的内容；
- 定义接受门槛和停止条件。

输出：评测计划、目标版本、设备范围、统计口径、验收表。

### Phase 1：冻结对象和环境

- 记录源码/归档 hash；
- 创建隔离容器和设备映射；
- 记录 pre-state；
- 检查 CANN/Python/Torch NPU；
- 确定 root/UID 写入边界。

硬门禁：目标卡空闲，版本与映射可解释。

### Phase 2：私有构建与加载验证

- 按项目约束完成两阶段构建；
- 安装到版本独立私有 OPP；
- 构建调用 wheel；
- 记录包内容和 hash；
- 最小调用 bitwise 检查；
- `dlsym`/`dladdr` 验证目标 API。

硬门禁：源码、包、运行符号三者一致。

### Phase 3：正确性

- 固定规格；
- 随机种子；
- API 契约；
- 边界和特殊位模式；
- 高风险 repeat10。

硬门禁：全部通过，失败即停止。

### Phase 4：校准

- 每卡 tiny + large；
- 组内 CV；
- 卡间 P50 极差；
- 异常卡检查并重测一次；
- 生成 include/exclude manifest。

硬门禁：至少两张可解释设备，聚合只使用纳入卡。

### Phase 5：多轮延迟

- 固定 30 task；
- 丢弃首条；
- 确定性乱序；
- 多卡串行轮次；
- task 数/BlockDim 硬断言；
- 输出 task、case-round、case、round 四层 CSV。

硬门禁：所有原始 profile 完整且模型一致。

### Phase 6：Tiling/Kernel 模型

- 复现 Host 路由；
- 复现 Kernel tile/交集/DMA；
- 计算理论分支和成本；
- 与全部 profile BlockDim 对齐；
- 用微基准验证边界转折。

硬门禁：模型不一致则先修模型/环境/分组，不进入瓶颈归因。

### Phase 7：深度采集

- 选择覆盖不同成本结构的锚点；
- 三卡七组 metric + sample；
- metric 内 30-task 分组；
- SQLite 只读解析；
- 缺失字段和无效 `task_cyc` 显式标记；非零时继续验证映射与换算口径。

硬门禁：每份 profile task 数完整，指标字段口径清楚。

### Phase 8：四步分析

- Step 1 Tiling 建模；
- Step 2 按算子类型执行或显式跳过卡间流水；
- Step 3 按同步语义执行或显式跳过核间流水；
- Step 4 按固定优先级判 Bound；
- 将 ratio、带宽、L2、conflict、BlockDim、DMA 模型和波动交叉解释。

输出：证据排序的瓶颈和单变量候选，不直接修改实现。

### Phase 9：候选 A/B 与官方闭环

- 单变量实现；
- baseline/candidate 独立包；
- AB/BA 多轮；
- 总体、局部、回归、结构四类门槛；
- 官方逐 case 反馈确认泛化收益；
- 失败候选保留证据并撤回默认实现。

## 19. 结语

可复用的算子性能工程，本质上是把“版本、环境、用例、统计、模型、指标和结论”连接成一条可以被程序拒绝错误状态的证据链。

最重要的实践不是采集更多数据，而是：

- 在运行前证明测试的是目标版本；
- 在性能前证明所有关键语义正确；
- 在汇总前证明 task、顺序和 BlockDim 完整一致；
- 在归因前用模型证明实际执行路径；
- 在优化前区分 tiny、带宽、发射、并行和同步成本；
- 在发布前用多轮全局门禁否决局部但不泛化的方案；
- 在报告中诚实保留不可用指标和证据边界。

做到这些后，profiling 才不只是一次测量，而是能持续支持下一轮单变量优化、回归定位和官方提交决策的工程系统。
